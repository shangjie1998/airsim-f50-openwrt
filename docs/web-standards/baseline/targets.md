# 目标环境矩阵

> 所有前端建议只对下面这几类环境负责；表外环境出问题不修，只记录。

## 一、目标环境

| 编号 | 环境 | 怎么算这个环境 | 地位 |
|---|---|---|---|
| T1 | iPad Safari | 手上 iPad（iPad mini A17 Pro / iPad Air）系统自带 Safari | **主力**，一切以它为准 |
| T2 | macOS Chrome / Edge | M4 Mac mini，桌面浏览器最新版 | 次要：功能不得差于 T1，允许观感更好 |
| T3 | 旧版 Safari / 安卓系统浏览器 | 别人临时拿来访问 | 只保「能看能用」，不保观感 |

**不在负责范围**：Firefox、Windows 浏览器、设备自带 WebView（设备本身没有浏览器界面，页面从来是外部浏览器访问）。

## 二、三条硬约束（由部署形态决定，不是偏好）

### 1. 页面必须离线自足，不许依赖任何外部域名资源

设备平时是有网的（家里 Wi‑Fi 或蜂窝）。但有三类时刻设备和浏览器会同时上不了外网，这时页面必须照样完整可用：

| 场景 | 状态 |
|---|---|
| 关掉移动数据省流量，Wi‑Fi 又还没配好 | 设备无外网，浏览器也无 |
| 拨开关进「Wi‑Fi 待配置」，热点已关、Wi‑Fi 未连 | 只剩 USB 口 `192.168.77.1` 能管，无外网 |
| 户外信号差 / 欠费 / 限速 | 页面加载到一半卡死 |

推论：字体用系统字体栈，图片本地，不引 polyfill / CDN / 图床。固件页面本质是离线工具，不能把可用性押在第三方网络上。

### 2. 慢在接口，不在渲染

页面渲染在 iPad / Mac 上，硬件不弱。真正慢的是设备侧：每次 rpcd / ubus 调用都要 fork 外部命令，首屏多调十次就叠出几百毫秒。渲染侧唯一的真风险是毛玻璃大面积叠加在 iPad 上掉帧。

推论：首屏接口调用次数写进验收；`backdrop-filter` 层级 ≤ 2 且不进滚动容器。

### 3. 明文局域网不是安全上下文

LuCI 走 `http://192.168.77.1` 或 `http://192.168.x.x`，浏览器判定为非安全上下文。以下能力不可用，不要为它们设计交互：Clipboard API、Notification、Service Worker、WebAuthn、`navigator.geolocation`、绝大部分 `crypto.subtle`。

推论：页面上的复制功能（SSH 命令、配对码等）不能只依赖 `navigator.clipboard`，必须带「手动选中/文字提示」的降级；现有 `audio.js` 的「复制命令」就是这么写的（先判存在，失败给提示），照抄即可。

## 三、判定规则

- 一个特性只有在 **T1 上真机跑过一次**，才算「可用」，才允许升到 css.md 的 A 档。
- 同一功能优先选 T1 原生支持的写法，不为 T2 引入额外代码。
- T1 与 T2 表现不一致时：按 T1 写，T2 用 `@supports` 微调，**不许反过来**。
- T3 不做兼容投入，只保证「不出白屏、按钮能点」。

## 四、每次页面变更必须留的证据

| 证据 | 要求 |
|---|---|
| 截图 | iPad Safari 真机截图，不接受桌面浏览器截图代跑 |
| 特性登记 | 新用到的特性勾进 `css.md` 对应档，并从 C 升级/降级 |
| 接口次数 | 首屏接口调用次数写进交付说明（见 L3 人工项） |
