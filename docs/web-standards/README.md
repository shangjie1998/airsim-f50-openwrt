# 前端规范体系

我们自己的 Web 前端规范库：**基线先定「什么能用」，项目再定「必须怎么写」，交付最后逐条过闸。**

参考来源：`GoogleChrome/modern-web-guidance-src`（Chrome/Edge/Firefox/MDN 维护的 agent 技能库）。只抄骨架，不照搬内容——它的基线是现代浏览器，我们的基线是 iPad Safari + 弱算力 + 可能无外网。

## 三层

| 层 | 回答的问题 | 目录 | 状态 |
|---|---|---|---|
| L1 基线 | 什么能用、不能用时怎么写 | `baseline/` | **已完成** |
| L2 项目约束 | 这个项目必须怎么写（MUST / MUST NOT 断言） | `projects/` | 待建 |
| L3 交付闸 | 交付前怎么逐条核对 | `scripts/` | 待建 |

## 现在有什么

```
baseline/
├─ targets.md    # 目标环境矩阵：T1 iPad Safari / T2 桌面 / T3 兜底 + 三条硬约束
└─ css.md        # CSS 能力卡：A 已实测 / B 成熟 / C 谨慎 / D 禁用
```

## 怎么用

1. **动手写页面前**：查 `baseline/targets.md` 确认目标环境，查 `baseline/css.md` 确认想用的特性在哪一档。
2. **C 档特性**：不许直接上主线流程；要用就先单独验、单独写降级，验过再升 A。
3. **交付前**：iPad Safari 真机截图 + 首屏接口调用次数，写进交付说明（L3 建好后会变成脚本检查）。

## 评估制度（硬规矩）

**任何页面审计、任何新页面交付，MUST 至少三遍独立评估，且三遍方法必须不同**——同一手段重复三遍只是复读，不算数。

| 遍 | 方法 | 目的 | 典型动作 |
|---|---|---|---|
| 第一遍 | 静态扫描 | 找结构性冲突 | grep 模式 + 对照基准指南断言，出候选清单 |
| 第二遍 | 换视角反证 | 专门找第一遍的**误报与漏报** | 读代码上下文，质疑「是不是我看漏了」「是不是本来就合规」 |
| 第三遍 | 量化裁定 | 钉死结论 | 逐条计数、跑实测命令，把每条改成确定数字或事实 |
| 第四遍（条件） | 真机实测 | 只在前三遍有出入时启用 | 浏览器/设备上真跑，看焦点、读屏、实际渲染 |

配套三条：

- 每遍方法必须不同，**不许换个措辞把同一份结论再说一遍**。
- 审计结论 MUST 分级（P0 / P1 / P2 / 不改），每条写清收益与代价；没分级的审计不算交付。
- **评估轮不动代码**。评和改分开，改之前结论先落文档，避免「边审边改、越改越乱」。

历史验证：`2026-11-13` 对 AirSIM F50 十个视图做三遍评估，第一遍有两处分级判错（字号成本高估、复制提示缺陷低估），第二遍翻出、第三遍裁定修正。这就是三遍制的价值所在。
