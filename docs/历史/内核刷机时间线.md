### 手动按依赖顺序复载后的定位（临时态，重启不保留）

开机脚本的加载顺序有问题，不是单纯"内核把 SoC 关死了"：

1. `snd-compress.ko` 先加载（rc=0），再 `snd-soc-core.ko` 即可 rc=0；开机时顺序反了，core 先摸 `snd_compress_new` 报 Unknown symbol，失败后不再重试。
2. `snd-soc-sprd-card.ko` 只依赖 core 和内核通用符号，**应先于 codec/vbc 加载**并导出 `arch_audio_*_gpr`、`agcp_ahb_gpr_null_check`、`get_sp_audio_debug_flag` 等私有符号；codec/vbc 再挂。开机顺序把 codec/vbc 排在 card 前面，GPR 符号缺失成片报 Unknown symbol。
3. 按 `compress → core → card → power → codec-ump9620 → vbc-v4 → dmaengine-pcm → routing → compr → vbc-fe` 手动 insmod，除 `snd-soc-sprd-platform.ko` 缺失外其余基本 rc=0。
4. **CPU DAI / platform 待定位**：10.19.1 完整栈里 `snd-soc-sprd-platform.ko`（函数 `sprd_pcm_open/new/pointer/trigger`、`sprd_soc_platform_probe`、`sprd_pcm_driver`）经源码比对**就是 mainline 的 `sprd-dmaengine-pcm.c`**，自研包里 `sprd-dmaengine-pcm.ko` 已承担同一角色，**不是真缺项**。CPU DAI 在 5.4 归档是独立 `snd-soc-sprd-dai.ko`（`sprd_agcp_i2s_dai_probe` / `sprd_dai_probe`），6.18 编进内置 Image；现内核 builtin 已见 `sprd_fe_dai_dev_probe`、`sprd_dai_vbc_probe`、`asoc_sprd_card_dai_link_of`。
5. **link 57 根因已定死（2026-11-20 phandle 反查）**：DTS `sound@0/sprd-audio-card,dai-link@57`，日志名 `BE_FAST_P_SMART_AMP`（`BE_ST_FAST_P_SMART_AMP`）。sound-dai 反查：codec phandle 0x105(261)=`soc/ap-ahb/i2c@22a0000/aw883xx_smartpa@34`（compat `awinic,aw883xx_smartpa`）；cpu phandle 0x103(259)=`soc/agcp/vbc@56510000`（`unisoc,qogirn6pro-vbc`）；plat phandle 0x102(258)=`sprd-routing-pcm`（`unisoc,pcm-routing`）。**这颗 AW883xx 智能功放 F50 板上根本没有硬件**：I2C-6 地址 0x34 总线枚举到节点但无驱动绑定、无应答；它的 DAI 永久 `-EPROBE_DEFER`，ASoC machine probe 因这一条 link 失败而中止，整卡注册不出来。
6. **现成兜底补丁已在自研 card.ko 里**：`sprd-asoc-card-utils.c` 的模块参数 `dummy_on_defer`（bool，默认关）；codec 侧（`!args_count`）DAI 一直 defer 时改用 `snd-soc-dummy-dai` 兜底。设备 card.ko strings/modinfo 实证含 `parm=dummy_on_defer:bool`。dsp CLI `load_all` 加载 card 时默认传 `dummy_on_defer=${MU300_AGDSP_DUMMY_ON_DEFER:-1}`（即默认开），之后 `bind_card` 手动 unbind/bind `sound@0` 重探。
7. **现场为何没兜底**：今天设备上的音频 ko 是排查过程中手动 insmod 的临时态，card 加载时**没带**该参数（=0）；模块全标 `[permanent]`，rmmod 不掉，无法现场热重载带参。跑标准 `mu300-audio-dsp load` 仍 19/19 但卡未注册，dmesg 重探仍在 SMART_AMP codec `-517`。要验证兜底生效，需重启走 dsp 开机完整流程（reserve → CORE → DMA → MODULES 两遍带参 → bind_card）。
8. `audio_reserve.ko` 现场未加载（S10 脚本在位启用；开机流程会先跑 reserve 抢 0xaf700000/3MiB + 0xafa00000/6MiB）。
9. **配置对齐实证**：配件包 `KERNEL` 的 `CONFIG=233c7a62…` 与现内核 `/proc/config.gz` 哈希逐位一致，`audio_dir` 判定 DIR_OK；vermagic 6.18.60 匹配。

> 源码基础：本地 `kbuild/mu300-audio/kernel/mainline/sprd_audio/` 6.18 音频源码齐全（dai/vbc/fe、codec/ump9620、machine/sprd_card、platform 三子目录）；兜底补丁另见 `kernel/5.4/patches/sprd-card-dummy-on-defer.patch` 与 `_upstream-mu300-linux/kernel/patches/`。

> vermagic 门槛（2026-11-20 实测）：自研 25 ko = `6.18.60 SMP mod_unload aarch64`，与现内核匹配；10.19.1 完整栈 ko = `6.18.57`，5.4 档 ko = `5.4.254`，直接 insmod 会被 vermagic 拒绝，不能混装。ALSA 通用层（pcm/hwdep/timer/compress）现内核 builtin 齐全；SoC 框架符号由配件包 `snd-soc-core.ko` 外挂提供。

> **现内核结论（2026-11-20 重启实证通过）**：不动 6.18.60 内核，声卡已注册成功。干净重启后实测：`/proc/asound/cards` 出现 `1 [sprdphonesc2730]: sprdphone-sc273`；dsp status **19/19 loaded**；reserve **0 pages missing**（0xaf700000/3MiB + 0xafa00000/6MiB 预留成功）；DSP **running，首条命令即应答**，power-up yes。PCM 端点含 FE_ST_VOICE / VOICE_C / VOICE_PCM_P / MM_P / A2DP / BTSCO / BTCAP。根因不是内核焊死：板上没有的 AW883xx 功放由 `dummy_on_defer=1` 兜底，老版 dsp 脚本换回 517 修复版后 CORE/reserve 链路正常。

### 仍遗留（不影响声卡注册）

1. **通话 profiles blob 缺失**：`/lib/firmware/` 仅有 `agdsp.bin`，缺 `audio_structure` / `dsp_vbc` / `cvs`（/ `smartamp`）。status 提示数据通路还需这些 DSP 参数；本地 `tools/vbc-profile/vbc-profile.py` 构建工具在，但**厂商 XML 参数集本地无源**，需另找。缺它们时 PCM 打开可能 EIO，通话出声待补。

### profiles 来源排查与现场实测（2026-11-20）

**四个 blob 的消费方式**（mainline `vbc-dai.c`）：`vbc_profile_loading()` 经 `request_firmware()` 按名取 `/lib/firmware/<audio_structure|dsp_vbc|cvs|dsp_smartamp>`；由 mixer「* Profile Update」写 1 触发加载，`vbc_profile_put` 只在 `data[idx]` 已存在时 `try_apply`。**PCM 打开路径不主动取 firmware**，缺 blob 只让 Update 控件返回错误，不直接挡 open。

**来源已逐一排除**：
- 设备：`/lib/firmware` 仅 agdsp.bin + 蓝牙/GNSS/Wi-Fi 固件；无 `/odm/etc/audio_params`、无任何 profile blob/XML。
- 本地归档与源码树：`mu300-audio` / `mu300-linux` 源码、r16 source、5.4 工具归档、openwrt-packages 源码均无 `*.xml` 参数集，也无现成 `audio_profile` magic blob。
- 上游 Release：`mu300-audio-firmware` v1.0 资产只有 `agdsp.bin`；`kai-wu-cortex/mu300-audio` 树只有 vbc 驱动源码，无 XML。
- 唯一剩余来源：同 SoC（UMS9620 / T760，ZTE Voyage 41S / U30 Air）**Android 固件包**的 `/odm/etc/audio_params/sprd/*.xml`，或一台活着的同型号 Android 机从 /odm 提取；再用 `vbc-profile.py` 按 XML 构建四个 blob。

**现场实测（缺 profiles 状态下）**：
- 端点齐全：VOICE / VOICE_C / VOICE_PCM_P / MM_P / AP01 / AP23 / A2DP / BTSCO / BTCAP 等均列出。
- `hw:1,53` VOICE_PCM_P（16k mono）：open 成功，`write error: I/O error`（rc=1）。
- `hw:1,0` AP01（48k stereo）：open 成功，同样 write EIO；日志 trigger Start → 约 1.2s Stop → shutdown，SIPC cmd=5 往返成功（`aud_send_cmd out,cmd=5 repeat_count=1`，DSP 有应答），期间仅一次 `aud_smsg_recv cache is empty` / ENODATA 后重试成功；**无 profile/firmware 缺失报错**。
- `hw:1,55` MM_P：open 即 EINVAL，`no backend DAIs enabled for FE_MM_P`（路由未开，与 profiles 无关）。

**因果边界（未分离，勿下定论）**：EIO 发生在 write/DMA 数据阶段，DSP 场景命令已应答；日志未见 profile 缺失。EIO 既可能是缺 profiles 的 DSP 参数未下发，也可能是 DMA/buffer/场景路由问题。**在拿到 XML 补齐 blob 做对照之前，不能断定「补 profiles 就能出声」**。下一步若要继续：先取同 SoC Android 固件 XML → 构建 blob 落 `/lib/firmware` → `mu300-audio-dsp profiles` 加载 → 复测 write 是否还 EIO；若仍 EIO，再查 DMA/buffer 与后端 DAI 路由。
2. **脚本固化（2026-11-20 已在本地完成、闸二通过，待发布）**：权威 517 版落 `parts/audio/opt/bin/`，dsp 随 opt 包自带并加打包/安装双哈希闸门；详见下节「老版脚本回流路径复盘与固化」。重打 audio-opt 包、跑闸三上传仍需用户确认。
3. 现场 `mu300-audio-dsp.broken-20261120` 为坏版快照，未删；设备上残留的 `mu300-audio-dsp.orig`（471 `afd4e363`）是旧链路留的原版，新安装器不再生成 `.orig`，确认稳定后可清。

### 2026-11-20 重启后二层根因：dsp 脚本是老版（CORE 不 insmod、无 reserve）

重启基线实测：驱动仅 **10/19**，`/proc/asound/cards` 仍 Loopback；lsmod 无 `snd_soc_core`/`snd_compress`/`snd_soc_sprd_card`，dmesg 上层模块成片 `Unknown symbol snd_soc_register_component / snd_soc_dapm_* / arch_audio_*_gpr`（err -2）。

- 设备现场 `mu300-audio-dsp` 是 **471 行老版**：`CORE_MODULES="snd-soc-core snd-compress"` 加载只走 `modprobe`，不从配件包目录 insmod；而这两颗只在 `/mnt` 配件包、`/lib/modules/6.18.60/` 没有，modprobe 静默失败 → SoC 核心起不来 → 上层全挂。老版也**没有 reserve 分支和 reserve 调用**，`audio_reserve.ko` 开机不加载。
- 1.0.5 归档包里的修复版是 **517 行**（哈希 `6e254b35…`）：CORE 段配件包 ko 存在则先 `modprobe snd-pcm/snd-timer` 再 `insmod "$A/$m.ko"`；`load_all` 开头 `reserve || return 1`；有 `reserve)` case；card 带 `dummy_on_defer=${MU300_AGDSP_DUMMY_ON_DEFER:-1}`。
- 处置：设备坏版留快照 `mu300-audio-dsp.broken-20261120`，归档 517 修复版已推回设备并校验哈希一致。现场脏状态被 reserve 的 legacy 保护拦住（`loaded audio_mem` 且预留未验证 → `clean boot required`），需干净重启走 S10 reserve → prepare load_all 完整流程。
- 注意：`install.sh` 的 awk 补丁只改两处（set_fits 放行、aplay 探针不判死），不会删 reserve/insmod 逻辑；471 老版来源是更老一版上游脚本，非该补丁改坏。

### 471 是怎么回到设备的（证据链）

1. audio-opt 1.0.5 配件包**本身不含 dsp 脚本**（只给 `modules/<krel>/*.ko` + `integration/airsim-audio-reserve` + `install.sh`）。
2. 包内 `install.sh` 发现 `$EXT/bin/` 缺工具时，把五个可执行（含 dsp）一起从 thirdparty 归档 `mu300-audio-5.4.tar.gz` 补；该归档里的 dsp 就是 471 `afd4e363`。
3. 补齐后 install.sh 再跑一段临时 awk，按 471 的文本特征改两行（set_fits 放宽 true、aplay 探针 `return 1→true`），得到 471 微调版 `a6f6d63c`；未改的原件留作 `mu300-audio-dsp.orig`。
4. 471 缺的正是二层根因那两条：CORE 模块只走 modprobe 不从配件包 insmod、没有 reserve 分支。于是开机只起 10/19、声卡不注册。

### 为什么 517 修复版没走这条安装链路

- 517 只存在于 r16 那条 `package-openwrt-audio.py` 链路：它吃「已打补丁的隔离 audio source」，补丁是在隔离副本上手打的，**没有回灌到权威源码**。
- 面向真机安装的 opt 链路，工具脚本取自 5.4 legacy 归档；两条链路各走各的，517 一直躺在归档里，没进到安装器实际下载的工具集。
- 本地 `kbuild/mu300-audio` checkout 又是未打补丁基线（508），`guard-reservation.patch` / `startup-check.patch` 在本地源码树里查不到标记。

### 当时缺的三道闸门

- **打包不校验脚本身份**：`package-openwrt-audio.py` / `make-opt.sh` 直接取脚本进包，无哈希核对；取到哪版算哪版。
- **安装不校验脚本身份**：install.sh 不核对 dsp 哈希，靠现场 awk 打补丁兜底；补丁按 471 文本行号/特征写，换个基线就静默失配。
- **权威源缺失**：打过补丁的 517 只在临时隔离副本，仓库里没有一份「这就是发布该用的 dsp」的固定副本。

## 重编内核可行性（回应"我这台机器能不能编、要多久"）

- 硬件：Apple M4 / 16GB / 10 核 / arm64 macOS，性能够。
- 约束：macOS 不能直接跑上游 kbuild（host 工具链 objcopy / strip / pahole、ELF 处理是 Linux 那套）。两条路：云主机 4C8G 起 Ubuntu 交叉编；或 Mac 开 arm64 Linux 虚拟机原生编。
- 工时：只编模块约 1–2 h；全量 Image 约 2–5 h（4C8G）或 1–3 h（M4 虚拟机原生）。
- 前置障碍：先找回开 `CONFIG_SND_SOC_SPRD` 的 config 基线；确认展锐音频 port 源码仍在树。**现成带音频包优先于重编**（上表完整音频栈四颗 6.18.57）。
