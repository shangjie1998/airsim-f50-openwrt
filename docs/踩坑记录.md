# F50 插件踩坑记录

> 这份是**参考**，不是标准答案。每条都标注了当时的设备版本与时间，换了系统镜像、换了上游版本，具体现象会变，
> 但"先怀疑哪里"的顺序基本不变。真遇到问题：先按这里的顺序排一遍，再以现场现象为准。

设备基线：中兴 F50（UMS9620），OpenWrt `25.12.5 r33051-f5dae5ece4 armsr/armv8`，root 密码自设。
插件版本区间：`0.1.0.10` ～ `0.1.0.16-r23-6.18`（2026-10 ～ 2026-11）。

## 1. 刷机后插件装不回去 / 装上了服务不启（五个坑，按这个顺序排）

**现象**：`/usr/lib/airsim` 是空的、`ubus` 里没有 `airsim` 对象、`/etc/init.d/airsim: not found`；装完 `ubus call airsim status` 报服务不存在。

| 序 | 根子 | 怎么认 | 怎么修 |
|---|---|---|---|
| ① | `install.sh` 开头硬要求 `/usr/lib/airsim/airsim-mu300d` 存在，否则 `exit 1` | 安装日志第一行就退出 | 加 `FRESH=1` 分支：不备份、直接铺、`uci set airsim.main.enabled=1` + commit + `init.d enable` |
| ② | 包里只有 overlay 层，没有上游基础层 | 铺完 `files/` 里没有 `/usr/lib/airsim/*` 之外的运行时 | `make-package.sh` 先 `rsync -a src/plugin/packaging/openwrt/root/ "$STAGE/files/"` 再叠 overlay |
| ③ | `prepare` 里 `command -v mu300-at mu300-voice mu300-audio-dsp` / `amixer aplay arecord` 检查，刷机后只剩 `mu300-at` | `prepare` 日志第一个缺失项 | 从旧镜像补 `/usr/lib/airsim/bin`、`alsa/`、软链 `mu300-voice`/`mu300-audio-dsp`、`pcmhost`、`ctlset`、`/lib/firmware/agdsp.bin`（6,291,456 字节） |
| ④ | 音频模块与内核 ABI 不匹配（`insmod` 报 `struct module size must match`） | `dmesg` 里那一句 | 按内核重编（见 `docs/音频/配件包.md`），或换回旧镜像 |
| ⑤ | 号码读不出：新版 `mu300-at` 不支持 `-` 从 stdin 喂命令（`-` 被当 AT 命令发上去，回 `+CME ERROR: 0`） | `number_refresh` 空值 | `cp -n /usr/bin/mu300-at /usr/bin/mu300-at.fw-new`，再拷回旧镜像那个 `mu300-at`；修好 `number_refresh` 返回 `ok:true` 与号码 |

## 2. 装完"啥也没报错"但服务是 inactive（配置被覆盖）

**现象**：`ubus call airsim status` 回 `active with no instances`，进程数 0，日志干净。

**根子**：包里的 `/etc/config/airsim` 默认 `enabled='0'`，铺 overlay 时把设备上已经调好的配置盖掉了。

**修法**：铺完 overlay 后回拷备份里的配置（只拷 `config/`，别拷别处）：

```sh
if [ "$FRESH" = 0 ] && [ -d "$BK/config" ]; then
  for f in "$BK"/config/*; do [ -f "$f" ] && cp -p "$f" "/etc/config/$(basename "$f")"; done
fi
```

**认坑要点**：`enabled='0'` + `active with no instances` + 无错误日志 = 配置被覆盖，不是程序坏了。

## 3. 升级后 agent 反复重启（端口被占）

**现象**：`bind: address already in use`（8575），procd 报 `crash loop 6 crashes`。

**根子**：旧进程没退干净，新实例抢不到端口。

**修法**：再 `restart` 一次通常就好；反复出现说明 stop 阶段没等到旧进程退出，得在 stop 里加等待。

## 4. macOS 打的 tar.gz 到设备上被判"包结构异常"

**现象**：设备侧说找不到 `install.sh`，或者解出来一堆 `._xxx` 文件。

**根子**：bsdtar 会把 macOS 的扩展属性写成 `._` 影子文件，Linux 侧当普通文件。

**修法**：

```sh
COPYFILE_DISABLE=1 tar --no-xattrs --no-mac-metadata -czf out.tar.gz ...
```

## 5. 手工往设备传了页面，浏览器还在跑旧代码

**现象**：`maintenance.js` 明明换了，页面还是老样子；控制台可能是 `ui.menu is not a function` 这类旧代码报错。

**根子**：LuCI 的 `?v=` 资源版本号来自包数据库 `/lib/apk/db/installed` 的 mtime。

**修法**：传完文件 `touch /lib/apk/db/installed`；改 CSS 还要同时升 `ui.js` 里的 `CSSVERSION`。老标签页仍吃旧 `luci.js` 时开新标签页。

## 6. 来电转发"跟随短信转发"填了却测试失败

**根子**：地址/密钥没从短信转发那套配置源里取，取到的是空值；HTTP 200 也可能是业务失败。

**认坑要点**：先回读一次真实配置源（`uci get` / `jsonfilter`），再比对 HTTP 返回的 body，不要只看状态码。

## 7. 页面渲染出 `[object HTMLDivElement],[object HTMLDivElement]`

**根子**：自建 LuCI 页面把 `E()` 的 children 传成了嵌套数组，渲染层不报错，直接把数组转字符串。

**修法**：`E()` 的 children 先摊平成一层再传。

## 8. 信号强度恒为空 / `99,99`

**根子**：`AT+CSQ` / `AT+CESQ` 在 5G SA 下只回占位值。

**修法**：改用厂商数据源 `ubus call mu300.modem signal '{"slot":"0"}'`。

## 9. 刷机后「音频/蓝牙各缺一处」，看着像内核问题其实是缺件

**症状**：换回 6.18.60 内核，模块数、符号、vermagic 全对，音频却死活不响；蓝牙页点开关报「脚本不在位」。这两件事最容易被误判成「内核不适配」。

**四处缺件（各回各家，主包一个字节都不带）**：

| 缺件 | 归谁 | 表现 |
|---|---|---|
| `/etc/init.d/airsim-audio-reserve`（S10） | 音频配件包 | `/sys/module/audio_reserve/parameters/missing` 远大于 0，日志 `N pages not taken`。该脚本要在开机最早抢一段固定物理内存，晚了页已被 slab/匿名页占死且不交还（`CONFIG_COMPACTION=n`），只能重启重来 |
| `modules/<KREL>/KERNEL` | 音频配件包 | `prepare` 报 `built for another build of it (): not loaded`。`set_fits()` 拿这里的 `CONFIG=` 与 `gzip -dc /proc/config.gz \| grep -E '^(CONFIG_\|# CONFIG_)' \| LC_ALL=C sort \| sha256sum` 比对，缺文件就是 `()` 对不上 |
| `/usr/sbin/f50-bt-switch.sh` | 蓝牙配件包 | `bt_set` 返回「蓝牙脚本不在位」 |
| `/etc/init.d/sprdbluetooth` + `/usr/sbin/sprd-bt-attach.sh` | 蓝牙配件包 | `hciconfig` 看不到 `hci0`、`/sys/class/bluetooth` 空、`attached=false` |

**已固化进包**（以后不用手工补）：

1. `parts/audio/opt/install.sh`：装完模块后把 `integration/airsim-audio-reserve` 落到 `/etc/init.d/` 并 `enable`（S10）；若包内没带 `modules/<KREL>/KERNEL`，按本机 `/proc/config.gz` 现算 CONFIG 补一份
2. `parts/audio/payload/6.18.60/KERNEL`：`CONFIG` 必须写**目标发布内核**的配置哈希（6.18.60 = `233c7a62…d4b5`），不能写构建套件那份（`d5628675…`）
3. 蓝牙三个文件本来就在 `parts/bluetooth/payload/root/`，`install-bt.sh` 会 `chmod 0755` + 逐个 `enable`——刷机后**重装蓝牙配件包**即可，不是要新增文件

**排查顺序**（别一上来怀疑内核）：`uname -r` → `ls /lib/modules/<krel>` 模块数 → `missing` 参数 → `prepare` 报错原文 → 最后才看 `ko_count`/vermagic。

**顺带**：`parts/audio/opt/install.sh` 里 `dest=$EXT/modules/$KREL_WANT` 是历史遗留死代码，在 `set -u` 下会直接 `KREL_WANT: parameter not set` 崩掉，已删。

## 自检脚本把 5.4 厂商内核判成"错误"（2026-11-11）

`airsim-postflash-check` 第 1 项原来只认 `6.18.*`，其余一律 fail：
`"$KREL 不属于 6.18 线，音频模块装不上"`。5.4.254 是厂商内核、语音模块内核自带，
结果刷机自检在 5.4 上永远 7/8、红一条，看着像坏了。

改法：三档都认（`6.18.*` / `7.3.*` / `5.4.*`），5.4 的说明改成"厂商内核，语音模块内核自带，不用配件包"。
判据必须跟 `docs/内核矩阵.md` 同步；再加一档就得回来改这里。

## 配件包"检查更新"永远显示已是最新（2026-11-11）

`audio_opt_latest` 里 `_cur=${TAG#audio-opt-v}` —— 拿包里钉死的 TAG 当"已装版本"。
于是设备上装着 1.0.2、最新是 1.0.3，页面照样显示"已是最新"。

改法：`_cur` 先取 `status_field version`（安装器写的状态），再退 `EXT/audio-opt-version`，最后才退 TAG。
判"有没有新版"必须拿**设备上的实际版本**比，不能拿代码里写的常量比。

## VERSION 升了、二进制没重编就打包：包发出去标签和内容对不上

**症状**：页面/`ubus call airsim status` 报 `0.1.0.18-r23-6.18`，而 `/usr/lib/airsim/VERSION` 写的是 `0.1.0.23-r23-any`。重启主服务也不变——不是进程没重启，是二进制里那个串本来就旧。

**怎么查**：`strings` 打一下包里的二进制，看里面有几个版本串：

```sh
tar xzf dist/airsim-f50-0.1.0.23-r23-any.tar.gz -C /tmp/x airsim-f50-0.1.0.23-r23-any/airsim-mu300d
strings /tmp/x/airsim-f50-0.1.0.23-r23-any/airsim-mu300d | grep -oE '0\.1\.0\.[0-9]+-r23-[a-z0-9.]+' | sort -u
```

只认出一个旧串，就说明包里的二进制是旧的。

**根因**：版本串是 `overlay/f50/build.sh` 用 `-ldflags -X main.version=$(cat VERSION)` 注进去的，而 `build/make-package.sh` 只是 `cp out/f50/*` 到暂存目录——**VERSION 是每次现读的，`out/f50` 却可以是几天前编的**。中间只升号不重编，就得到"新标签 + 旧内容"。

**现在怎么防**：`build/tools/check-consistency.py` 第 5 项直接 `strings` 两个二进制，内嵌版本必须等于 `VERSION` / `AGENT-VERSION`，不等 `exit 1` 拒绝打包，并提示先跑 `overlay/f50/build.sh`。反例实测能拦。

**规矩**：升完号（`build/bump-version.sh`）之后，**必须先重编再打包**，别直接 `make-package.sh`。

## 配件包下载器写死单个内核：7.3.1 上点"安装"必失败

**症状**：7.3.1 上在「音频」页点安装，返回 `state=failed`、`失败：本机内核 7.3.1，音频可选件只给 6.18.60 用`。

**根因**：配件包本身没问题——`airsim-f50-audio-opt-1.0.3-k6.18.60+7.3.1.tar.gz` 里两套模块都在（`modules/6.18.60`、`modules/7.3.1` 各 25 个），包内的 `install.sh` 也是多内核的。坏在**外层下载器** `/usr/libexec/airsim-audioopt-install`（主包带的那个）里写死：

```sh
KREL_WANT=6.18.60
[ "$krel" = "$KREL_WANT" ] || die "..."
```

档位只认一个，另一套模块等于白打。rpcd 的探测口径（`OPT_KERNELS="6.18.60 7.3.1"`）是对的，所以页面显示"可装"，点下去却被下载器拒——两处口径不一致的典型。

**修法**：下载器改成白名单，与 rpcd 同一份：

```sh
OPT_KERNELS=${AIRSIM_OPT_KERNELS:-"6.18.60 7.3.1"}
case " $OPT_KERNELS " in *" $krel "*) ;; *) die "..." ;; esac
```

`check-consistency.py` 加一项：下载器白名单 == rpcd `OPT_KERNELS` == `parts/audio/payload/` 下的目录，三处不同就拒绝打包。

**还有个坑**：模块装好当次不生效——加载走开机 `prepare`，必须重启一次才出声。

## firewall 规则不写 device，就等于对所有入口放行

给管理页开 80/443 时图省事写了 `src='*'` 的规则，fw4 渲染成 `tcp dport { 80, 443 } accept`——没有 `iifname`。5.4 时这条还加载不进去（flowtable 那个死结），到 7.3 上规则真进表了，隐患才露出来：切到「手机流量」模式，`wan` 通公网，管理页就挂在运营商网络上。

fw4 的 rule 支持 `option device`，渲染成 `iifname "wlan0" tcp dport { 80, 443 } accept`，只认无线口。管理页开关就按这个写，并把"蜂窝口永远不放"写进页面文案里——不给用户"忘了关"的机会。

## `mu300-update` 不认 7.3：改的是设备本地脚本，换系统即失效（2026-11-11）

现象：`mu300-update kernel 7.3` 直接报档位不支持，而 `7.3` 的包明明已经下好。

原因：设备上 `/opt/mu300/bin/mu300-update` 的 `KERNELS` 是 `5.4 6.18 7.2`，没有 `7.3`；这行是上游维护的，不随我们的包走。

当时的处理：`sed` 把 `7.3` 加进 `KERNELS`，并在 `kernel_cmd` 的 `case` 里补 `7.3` 分支；原文件备份到 `/mnt/mu300-disk/pkg/mu300-update.bak-20261111`。之后 `MU300_RELEASE=v2026.11.02.1 MU300_KERNEL_BUNDLE=... mu300-update kernel 7.3` 正常返回 0。

**要记住的**：这属于设备本地补丁。`mu300-update apply`（换整套系统）会用上游脚本覆盖回来，届时 `7.3` 档位又会消失。换完系统先 `grep '^KERNELS=' /opt/mu300/bin/mu300-update` 自查，不对就按上面补；详见 `docs/内核矩阵.md` 的「换内核怎么换」。

## rpcd 的参数走 stdin，不是 `$3`；页面开关点了没反应就是这么来的（2026-11-11）

现象：联网页的「管理页面访问」开关点下去，永远回一句 `enable 只接受 1 / 0`，页面状态不跟手。命令行里 `sh /tmp/airsim-net-new call admin_set '{"enable":1}'` 却一切正常。

两层原因叠在一起：

1. **参数位置**。`/usr/libexec/rpcd/<名字>` 这种 exec 插件被 rpcd 调用时，argv 只有 `call` 和 方法名，**调用参数是从 stdin 灌进来的 JSON**（`$1=call`、`$2=admin_set`、`$3` 为空、stdin=`{"enable":1}`）。脚本里写 `admin_set "$3"`，正式路径下永远是空参数；手动 `sh 脚本 call 方法 '{...}'` 调试时参数在 `$3`，所以本地怎么测都通过。
   → 改法：`call)` 分支里先看 `[ -t 0 ]`，非终端就读 `cat` 拿 stdin；`${3:-}` 只作为手动调试的兜底，两条路都留。

2. **jshn 只认字符串**。`json_get_var enable enable` 遇到数字 `1/0` 拿到的是空值，于是校验直接打回。页面 rpc 声明的是 `String`，但传数字会被序列化成数字。
   → 改法：后端不再走 jshn，把参数去掉空白后按原文匹配 `"enable":1 / "enable":true / "enable":"on"` 这一类，字符串、数字、布尔全收；前端统一传 `'1' / '0'`。

同批受影响的还有 `mode_set`、`wifi_connect`——它们也读 `$3`，都会变成"点了没反应"。改完用 **`ubus call`** 复验（不要只用手动 `sh` 跑脚本），三种形式（数字 0 / 数字 1 / 字符串）都要过一遍。

### 页面打开快慢不一样：慢在两处“每调用一次都要 fork”的地方（2026-11-11）

现象：9 个菜单页里「联网」明显慢，其余几乎一样快。用浏览器 `performance` 采导航计时，HTML 层都在 53~101 ms，看不出问题——**慢的是页面首屏那几个 ubus 调用**，不在 HTML。

实测（`/usr/bin/time`，单位秒）：

| 调用 | 修前 | 修后 |
|---|---|---|
| `airsim-net status` | 2.98 | 0.18 |
| `airsim-net probe` | 0.50 | 0.07 |
| `airsim-net wifi_saved` | 0.51 | 0.08 |
| 联网页首屏到出卡片 | 4.29 | 0.52 |

两个真凶：

1. **`airsim-netmode` 启动时把探测脚本连调 5 次**（一次一个键）。探测脚本本身就有 `-p` 一次给全部键，改用 `p_many` 一次取回、`sed` 按键取值，启动段 0.35 s → 0.06 s。
2. **探测脚本用 `iw dev` 找无线口，这一条就 0.41 s**（整个探测 0.5 s 基本全花在这）。改成看 sysfs：`/sys/class/net/<n>/phy80211` 存在就是无线口，几毫秒出结果。

教训：这颗 SoC 上 **每 fork 一次外部命令 60 ms 上下**（`$( )` 里再套一个 `awk` 也是一次），所以脚本里"循环调子脚本取单个键"的写法很贵；能一次取全的就一次取全。另外 `iw dev` / `iw phy` 这类命令能换 sysfs 就换 sysfs。

顺带修掉一处隐性错误：原代码 `AP_IF=$(p ap_if)` 取的 `ap_if` 这个键 `-k` 根本不支持（键名是 `live_if`），一直取空值再兜底成 `wlan0`；现在从 `-p` 的输出里正常取到真实 AP 接口名，非 wlan0 的机器不会再被兜底成 wlan0。

## 切 Wi-Fi 自检误判失败：别用「全局第一条默认路由」判出口（2026-11-11）

现象：页面上把上网切成 Wi-Fi，脚本报「外部 Wi-Fi 没连上（无 IP 或默认路由没落到无线口）」然后回滚，人却明明连上了。

复现看到的两条路由：

```
default dev sipa_eth0 proto static scope link                    # 蜂窝，切的时候还没断
default via 192.168.50.1 dev wlan0 proto static src 192.168.50.230 metric 20
```

`check_wifi()` 用的是 `route_dev()`（`ip route` 里第一条 `default` 的 `dev`）。切换是先连 Wi-Fi、确认拿到地址后才断蜂窝，这段窗口里蜂窝那条默认路由**一定还在**，于是无线口被误判成"没出口"，回滚把好好的 Wi-Fi 又关掉 —— 表现就是「开关点了没用」。

改法：

- 新增 `has_default_on <网卡>`，用 awk 扫完所有 `default` 行、看 `dev` 后一位是否等于目标网卡；`check_wifi()` 判 `has_default_on "$AP_IF"`，`check_cell()` 判 `has_default_on "$CELL_IF"`，都不再依赖"第一条"。
- `do_wifi()` 收尾补一段：`wan` 置 disabled 不一定会立刻摘掉那条默认路由（实测两条同时存在时蜂窝 metric 占先、出口仍走蜂窝），若蜂窝口还有残 `default` 就 `ip -4 route del` 摘掉，并确认全局只剩一条。

真机双向验证：`wifi → ap → wifi` 三次切换 `RC=0`，出口分别是 `wlan0 192.168.50.230` 与 `sipa_eth0`。

教训：**"第一条默认路由"在多默认路由存在的切换窗口里没有意义**，判据要按网卡（或按 metric）判，不能按顺序判。

## 通道模式从三档收成两态：单射频机器上本来就互斥（2026-11-11）

原来页面上是「手机流量 / Wi-Fi / 热点」三连按钮，实际设备只有两种稳定状态：

- 开：连外部 Wi-Fi 上网，`wan` 与 `ap0` 都 disabled（`110`）
- 关：用流量上网，热点同时开着（`011`）

`cell`（`011` 但 `ap0` 关）在单射频机器上没什么用（关着热点、又不用 Wi-Fi，等于只剩流量），留着只会让人猜哪档对。所以接口收成一个滑动开关「Wi-Fi 上网」，开走 `mode_set wifi`、关走 `mode_set ap`，`mode_set` 后端逻辑不变。

同时把首屏四个 ubus 调用合成一个 `screen` 方法（`probe` / `status` / `wifi_saved` / `admin_status` 在里面串起来跑），探测脚本只跑一次、把 `-p` 那份结果通过 `AIR_SIM_PROBE_CACHE` 喂给 `airsim-netmode`，省掉第二次探测：

| 指标 | 合成前 | 合成后 |
|---|---|---|
| `screen` 一次调用 | 4 次调用合计约 0.35 s + 4 次 rpcd 开销 | 0.21 |
| 联网页首屏 | 0.52 | 约 0.28 |

注意：`rpcd` 的 `list)` 和 ACL `luci-app-airsim-net.json` 的 read 列表都要同步加 `screen`，少一处就是页面白屏/403。

## LuCI 模块返回对象会报 "factory yields invalid constructor"（2026-11-11）

`glass.js` 第一版写的是 `return { css: css, switch: makeSwitch }`，页面直接白屏，控制台报：

```
TypeError: "view.airsim.glass" factory yields invalid constructor
  at luci-static/resources/luci.js
```

LuCI 装载模块时要求工厂交出一个**构造器**，直接返字面量对象不行。照着 `ui.js` 的写法改成：

```js
'require baseclass';
return baseclass.extend({ css: css, 'switch': makeSwitch, switchSet: setSwitch, switchToggle: toggleSwitch });
```

`baseclass.extend` 出来的类同时能当单例用，页面里 `glass.css()` / `glass.switch()` 照常调。
另注意 `switch` 是保留字，当属性名要加引号。

## 主题的复选框伪元素压不掉，开关只能换真 DOM（2026-11-11）

`input[type=checkbox]` 无论怎么 `!important` 清 `::before/::after`，真机上看到的还是「蓝胶囊 + 一个白勾」：
主题给复选框挂了渐变底和勾形伪元素，跟我们的圆钮叠在一起。计算值全对（56×32、圆钮 28×28、`left:2px`），像素上就是不对。

结论：**别再跟主题的伪元素打架**。开关做成 `button` + 一个 `span` 圆钮，状态放 `aria-checked`，
样式 100% 在自己手里，主题插不进来。点整行也能切换（行上的 click 判断 `ev.target` 不是开关本体才代理）。

## 公开仓库脱敏与历史重写（2026-11-11）

**症状**：GitHub 仓库（公开）的 README 表格里写着「实测 SIM `真实号码`」，`call-forward` 的 `test)`
分支里也硬编码了一个真实手机号。当前文件改掉之后，`git log -p` 翻两下还能看到原文。

**根因**：号码写进了**历史提交**，只改工作区文件不会让历史里的旧 blob 消失。

**做法**：

1. 先冷备份，再改。`git bundle create saves/pre-scrub-$(date +%Y%m%d%H%M).bundle --all`。
2. 当前文件换成明显假号（`+8613800000000` / `13800138000`）；文档写「实测可用（号码不写进仓库）」，
   别写「打码成 861*****5721」——留头尾照样能关联。
3. 历史用 filter-repo 精确替换（只动含该串的 blob，别的文件一个字节不动）：
   ```sh
   python3 -m pip install git-filter-repo
   printf '<真实号码已移除>==>861*****5721\n+86<号码已移除>==>+8613800000000\n' > /tmp/scrub.txt
   python3 -m git_filter_repo --replace-text /tmp/scrub.txt --force
   ```
4. 验证：`git log --all -S<号码>` 为空、`git grep <号码> $(git rev-list --all)` 为空、
   `git status` 干净（filter-repo 不动工作区）。
5. 证明不影响编译：`grep -rn "git describe\|git rev-parse" build/ parts/ overlay/` 应无命中；
   构建用的是 `go build -buildvcs=false -trimpath`，VCS 信息压根不入二进制；最后解包比
   `airsim-agent` / `airsim-mu300d` 的 **md5** 与设备上跑的一致。
   **别拿 tar 的 sha256 比**——tar 写 mtime，同内容重打一次 sha 就变，容易误判成"代码被改了"。
6. 强推：先 `push HEAD:main --force`，再 `push --tags --force`。远端由 API 建的 tag 本地没有，
   要 `git tag -f v0.1.0.26-r23-any HEAD` 补上，否则那个 tag 还指着含号码的旧提交。

**弱网下的强推**（实测踩过）：`curl 16 Error in the HTTP2 framing layer`、`SSL_ERROR_SYSCALL` 都不是权限问题，
是链路被打断。先量上行（1 MB 的 POST 到会返回 422 的地址）与 `git ls-remote` 连续成功率，
再用 `-c http.version=HTTP/1.1 -c http.sslVersion=tlsv1.2` 推。上行 40 KB/s 时 100 MB 历史基本推不动，
200 KB/s 才勉强够。

**留给下次的规矩**：这个仓库是公开的，文档/测试/示例里一律用假号；提交前跑 AGENTS.md §8b 里那两条扫描。
