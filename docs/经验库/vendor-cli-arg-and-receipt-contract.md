## 适用场景
上游程序（如 Go agent）用 exec 调厂商/第三方 CLI 脚本，报的是一句笼统的"未确认/提交失败"，而同一台机器上手工跑同一条脚本却成功。

## 关键做法
先读脚本正文判断它真正接受的参数形态（如 `grep -c -- '--stdin' 脚本路径`），按脚本实际支持的形态调用；能力判断在调用前做一次就定，不做"失败再换姿势重试"，有副作用的外发操作重试可能重复扣费。回执判据同步改成脚本真实输出：多行输出要加 `(?m)` 锚行首，格式有变体时用可选分组同时包容。最后用真实调用链（agent 接口返回 + 落盘状态文件）确认，而不是只看手工命令行成功。

## 踩过的坑
上游假定脚本认 `--stdin`，脚本却把它当号码、直接报"需要号码和正文"，上层把它翻译成"未确认"，把排查引向网络或余额；把号码和正文按位置参数传入即通过。回执正则只认 `sent (reference N)`，实际成功输出是两行 `submitting…` / `sent (N)`，行首锚且无多行标志导致成功被判失败——比真失败更糟，报文已发出，用户容易再发一次。另外外发失败后常有重复提交保护窗口（如 120 秒），复测要等过窗口；换号对比才能区分是代码问题还是运营商侧拒绝（如跨网短号返回 `+CMS ERROR: 313`）。

## 可复用的产物或模板
grep -c -- '--stdin' /opt/mu300/bin/mu300-sms   # 探测脚本是否认该 flag
`(?m)^sent \((?:reference )?[0-9]+\)$`          # 多行 + 变体回执正则
