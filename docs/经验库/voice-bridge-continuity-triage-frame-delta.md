## 适用场景
设备端语音桥（modem/DSP 语音经 ALSA 暴露，客户端走局域网 PCM）能双向出声，但用户报告声音断续，需要判断问题在本地采集/播放链、WiFi 传输还是运营商语音侧。

## 关键做法
语音桥通常暴露累计统计：下行帧、收到上行帧、转发上行帧、丢弃上行帧、静音帧。归因时不要看某一时刻的总数，而要在**通话进行中**按固定间隔反复拉取状态，只比较相邻两次采样的增量：
1. 通话建立后确认帧计数开始增长，且持续增长直到挂断；中途长时间不涨才说明本地链断了。
2. 关注丢帧计数（dropped/discarded）本通是否新增，以及静音帧占比。丢帧增量为 0、静音占比在个位数百分比，说明本地采集与转发链连续。
3. 同时确认 DSP/语音场景在通话中被拉起（如 scene running、指定 playback/capture 节点），挂断后正常退出。
4. 以上都成立时，把嫌疑转向传输侧：检查 AP 带宽/信道（80 MHz 宽信道在音频这种极低码率场景反而更易受干扰，可收窄到 20 MHz 复测）、客户端信号与重传统计，以及蜂窝侧信号质量读数。
5. 若帧计数不涨、丢帧持续新增或出现 ALSA xrun 日志，则先修本地链，再谈网络。

## 踩过的坑
- 这些计数是**跨通话累计**的，不随新通话重置。直接拿挂断后的总数当单通数据会误判成"这通一切都好"，必须取差值。
- 通话结束后计数冻结，事后查只能得到一段静止数字，无法判断断续发生的时刻——采样必须提前挂在设备上、在通话进行中做。
- 空闲时 DSP 未启动、语音场景 not running 是正常状态（按需拉起），不能据此判故障。
- 用采样输出的时间戳推算帧率不可靠：每轮采样若还调用了耗时的 AT 命令，间隔会被拉长，帧率估算失真；应以丢帧增量这类确定性计数为主要依据。
- 设备上不一定有 nohup，后台挂采样脚本要用 setsid 并重定向 stdin，否则随 ssh 断开被杀。

## 可复用的产物或模板
后台采样骨架（设备侧，setsid 脱离 ssh）：
```sh
setsid sh /tmp/callwatch.sh > /tmp/callwatch.log 2>&1 < /dev/null &
```
脚本每轮取状态并只打印关键片段，便于事后 diff：
```sh
st=$(wget -q -T 2 -O - http://127.0.0.1:<port>/status)
printf '%s %s\n' "$(date +%H:%M:%S)" "$(printf '%s' "$st" | grep -o '"audio":{[^}]*}')"
sleep 2
```
