## 适用场景
维护他人开源项目并在设备上覆盖安装的自建 LuCI 插件，页面之间风格不一致，用户要求"统一元素、适配不同终端、方便维护"，需要决定往哪个样式看齐或重做 UI 时。

## 关键做法
决定统一方向前，对每个页面的样式来源做三处归属核查：
1. 上游源码树（本项目 `src/`）里搜页面所 require 的共享模块是否存在——不存在说明不是上游带来的。
2. 覆盖安装脚本（`install.sh` 之类）里是否有安装该文件的语句——没有说明打包不带它。
3. 设备上该文件的实际位置与文件头注释、以及是否由其它既有面板提供——文件头自述"某面板共享模块"即为 vendor 资产。

三处都指向外部时，把该样式定性为外物：不纳入自己的设计系统、不作为统一目标，只在过渡期借用。统一方向应反过来——把依赖外物的那一页收编到自建样式（本项目 `as-root` + `overview.css`），其余页面不动。样式组织上，把单一大文件（汇集概览/表单/列表/弹层/拖拽区）拆成"设计系统 + 页面文件"两层，页面只写布局与逻辑，颜色间距只在一处定义。

## 踩过的坑
- 只看页面长得像"面板统一风格"就以为共享样式是上游或自带的，实际既不在上游源码里、也不在覆盖安装包里，固件一换、vendor 面板不在就整页白屏（`require` 到的模块为 undefined）。
- "主题感知"的 vendor 样式会跟随 LuCI 主题变色，测过的外观不等于用户实际看到的外观；写死样式反而可控。
- 全量重写的代价被低估：既有自建控件（弹层、拖拽区、双卡标签）都要重做，已有样式表基本报废；收编单页只是改一个文件加几十行样式。
- 中文提示的 shell 脚本里变量紧挨全角括号会被并进变量名，报 unbound variable，需用 `${VAR}`。
