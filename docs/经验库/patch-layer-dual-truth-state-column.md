# 补丁层双真值：功能改在源码还是补丁里，必须让机器分得清

## 症状

设备上某个功能（如页面里的"配对客户端在线状态"）突然不显示了，但源码里
明明有实现、构建也"成功"。

## 根因不是补丁没写，是两套真值

仓库设计是 `src/` 保持上游原样、改动只写 `*.patch`、构建时 `apply.py` 打进
合并树。但只要有一次**直接改 `src/` 并提交**，就同时出现两份事实：

- 补丁还在顶层，`apply.py` 照旧打 → 与已改的源码冲突，构建硬失败（这次就是：
  `AirSIM-pair-clients.patch` 4 个 hunk 里 3 个 reject，`build.sh` 直接中断）；
- 或者补丁被 `-N` 悄悄跳过 → 二进制缺功能，而构建"成功"。

两种都很坏，前者让你编不出东西，后者让你编出个残缺的东西。

## 修法：状态列 + 标志串校验

`patches/manifest.tsv` 加第二列状态：

- `active`：必须在构建时打进树里，打不上构建失败；
- `merged`：功能已写进 `src/`，补丁移到 `patches/merged/` 不打，但必须在树里
  找得到"已合并标志串"，找不到构建失败。

校验点是"源码里有没有这功能"，不是"补丁文件在不在"，所以同步上游把改动
冲掉时也会被拦住——这是它能替代"人记得住"的关键。

## 验收方法（必须做负向测试）

正向：`sh overlay/f50/build.sh` 通过，产物里 `strings` 能查到各补丁的标志串。
负向：把 `src/` 里那段功能抹掉（在临时树里做，别动真源码），再跑
`apply.py`，**必须**以非 0 退出并报"标了 merged，但源码里找不到 xxx"。

注意 shell 判据：`python3 x.py | tail` 取到的是 `tail` 的退出码，要用
`cmd > log 2>&1; rc=$?` 才拿得到真退出码。

## 顺带纠正的两个误判

- `check-patches.py` 不在 `overlay/f50/`，在 `build/tools/`，`build.sh` 有调用。
- 只看"补丁数对得上"不够，符号可能被 Go 内联/裁剪掉，要么选独特的正则/文案串，
  要么按功能分产物（plugin 与 agent）分别查。
