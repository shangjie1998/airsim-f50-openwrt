## 适用场景
同一设备存在多条内核线（如旧厂商 5.4 与自编 6.18），仓库里还留着只在旧线上有用的设备侧补丁、联调脚本、一次性修复脚本，要判断它们现在还有没有用、要不要从包里清掉。

## 关键做法
判断依据不是脚本注释或文档说法，而是**设备当前实际状态**。逐项到设备上核：补丁文件是否还在原位、里面的改动是否还在（可能已被更新工具覆盖回原版）、脚本当年改的配置是否已经落盘且生效（`uci get` 查值、`nft list` 看对象是否已消失）。三项都指向“已不需要”时，按“挪走不硬删”处理：移入 `archive/<旧内核线>/` 保留原件与 diff 以便追溯重放，同时删掉 `dist/` 里的副本和校验清单对应行，并把仓库内所有引用路径改到新位置，在归档目录 README 顶部写明为什么归档、新线为什么不需要。

## 踩过的坑
只按仓库文档判断会误判：设备侧补丁被 `mu300-update` 覆盖回原版后，文件还在但改动已没了；而一次性修复脚本改的 `flow_offloading=0` 早已落盘生效，脚本本身不再需要跑。两种情况都表现为“文件还在、功能其实由别的机制承担”。所以务必先查设备再定去留，并且不要顺手回滚那些已经落盘、留着也无害的配置。
