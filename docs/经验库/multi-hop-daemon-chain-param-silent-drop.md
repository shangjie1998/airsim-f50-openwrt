## 适用场景
自建网关类设备上，一个动作要跨多层才到硬件（如网页 → rpcd 脚本 → 本地 daemon → 后端 agent → AT 命令）。给动作新加一个可选参数后，页面和接口都不报错，但设备实际按默认值执行。典型信号：选了副卡，通话却落在主卡。

## 关键做法
把"参数到底传到哪一跳"当成独立问题查，不要以页面无报错为准。逐跳核对文件是否真被替换：在每层落地点用带特征字符串的自校验（如 `grep -c <新字段名>` 应为预期条数，配合 `md5sum` 与本地编译产物比对），异常值为 0 就是那一跳没更新。定位到缺的那跳后只补那一层、重启对应服务，再用**绕过上层 UI 的命令行直调最外层入口**复现同一参数，并从硬件侧取原始状态（如逐槽 `AT+CLCC`）确认效果，而不是看接口返回的"已发送"。

## 踩过的坑
多条 `scp` 连着跑、后一条覆盖了前一条的输出，中间那层的上传静默失败，被我按"已装机"处理。页面看着完全正常（下拉在、按钮能点），只是参数在网关丢掉了，直到通话落在错误卡槽才发现。教训：装机后对每一跳分别做字符计数或 md5 回读，别把"文件推过"等同于"内容到位"；批量上传时逐条看结果，不要用 `tail -1` 取合并输出。

## 可复用的产物或模板
```
# 逐跳核对
grep -c "<新字段>" /path/to/rpcd/script   # 期望与改动处数一致
md5sum /opt/bin/<daemon>                  # 与本地编译产物比对
# 绕过 UI 直调最外层入口验证
ubus call <obj> <method> '{"...":"<新参数值>"}' 
# 从硬件侧取原始状态（UNISOC 逐槽）
for s in 0 1; do MU300_SIM_SLOT=$s at -t 3 "AT+CLCC"; done
```
