## 适用场景
某个程序不直连硬件，而是读一个由厂商守护进程维护的旁挂目录/文件池（每条消息一个文件），在另一台设备上该守护进程不存在、只能自己造数据填进去时。接口往往只返回一个笼统错误串（如 “xxx pool unavailable”），不告诉你哪一行不合规。

## 关键做法
1. 先看接口的返回分层：列表接口常把真实原因抹成固定文案，状态接口里的 `last_poll_error` 才是解析器原话。先取状态接口拿到具体错误，再动手。
2. 直接读解析函数源码，逐项核对契约：头部与正文的分隔符（可能要求真正的空行 `\n\n`）、头部键值分隔符（可能是 `key: value` 冒号加空格而不是 `key=value`）、必填键、文件名与 `id` 字段是否必须一致、正文末尾换行。
3. 长度字段优先按 **UTF-8 字节数** 算（解析器通常比较 `len(bytes)`）。中文按字符数算会短一半，直接判定条目非法。
4. 字段值可能有额外约束（如 `scts`/时间戳需可解析、`dir` 需为特定值、`mo` 条目会被跳过）。
5. 造一条最小合成条目验证能被读出，再从目标系统的原生来源自动镜像进池子。

## 踩过的坑
- 只看“list 接口报 unavailable”会以为目录不存在或权限问题；实际是解析器拒绝格式，目录一直在。
- 头部用 `=` 写、`length` 用字符数写，两次都得到同一个 `invalid ... pool entry`，看不出差异。用 `od -c` 逐字节回读文件才确认。
- 只在“列表接口”上验证会一直失败；改为看状态接口的 `last_poll_error` 才拿到“条目非法”这条关键信息。

## 可复用的产物或模板
- 排查顺序：`GET .../status` 取 `last_poll_error` → `od -c` 回读落盘文件 → 对照解析源码逐字段核对。
- 写池子条目时用 `len(text.encode("utf-8"))` 生成 `length`，并先用一条合成条目验证读通再删掉。
