## 适用场景
在单片机/模组固件（如 LuatOS 项目）中给短信、来电、上线等事件接入一个带队列重发的第三方推送接口（pushplus、企业微信、钉钉、gotify 等），需要决定发送失败后要不要重投。
## 关键做法
1. 不要拿 HTTP 状态码当发送结果。这类接口多为异步受理：HTTP 200 只代表服务端收到请求，正文里还有业务码（如 pushplus 的 `code`）和流水号，必须解析 body 再判断。
2. 按业务码分级：系统异常（如 500）返回可重试错误，交给队列重发；账号次数超限（如 900）、令牌无效（903）、未实名（905）、积分不足（888）等属于重发无效，直接按成功处理、丢弃该条，否则会把账号越推越死。
3. 队列重发失败次数要设上限，并在队列层对全网失败做退避（如连续失败后开关飞行模式重连），不要裸循环重投。
4. html 模板类接口不会把 `\n` 渲染成换行，发正文前需自行把 `\r\n`/`\r`/`\n` 统一成 `<br/>`，并转义 `&`、`<`、`>`，否则短信内容里的尖括号会被当标签吞掉。
5. 群组/一对多推送用 `topic`（群组编码）字段，注意官方限制：webhook 渠道下 topic 无效；App 渠道可用。
## 踩过的坑
只兑 HTTP 状态码就会把业务失败当成成功静默丢掉，或者反过来把「账号已超限」的失败不断重投；pushplus 官方文档明确指出 900 代表请求次数过多、账号会被限制（单日超 1000 次封 7 天），继续请求只会加长限制。其次是 html 模板下发多行短信，不转 `<br/>` 会全部挤成一行，且正文里的 `<`、`&` 会被解析破坏。
## 可复用的产物或模板
pushplus 请求体：`{"token":"<TOKEN>","title":"<标题>","content":"<已转义并换行的正文>","template":"html","channel":"app","topic":"<群组编码>"}`，POST 到 http://www.pushplus.plus/send 即可。
