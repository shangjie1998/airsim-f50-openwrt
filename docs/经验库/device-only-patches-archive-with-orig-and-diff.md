## 适用场景
接手一台"已经调通"的嵌入式设备要做源码归档/交接，却发现仓库源码与上游 release 逐字节一致、看不出任何适配痕迹时。典型于插件包只覆盖 `/usr/lib/...`，而让人能跑通的改动落在 `/opt` 或别的运行库路径上。

## 关键做法
1. 先用 `diff -r`（忽略 vendor/out）把仓库源码与上游解包对比，确认"源码没改过"，这条结论本身就是交接文档里最该写清的一句，否则后来的人会在源码里空找补丁。
2. 到设备上定位真正被改的运行时文件：比对 `ls -l` 的字节数与时间戳、`sha256sum`，并找同目录的 `.bak-*` 原件。哈希先用 `sha256sum` 在设备侧记下，作为取回后的校验基准。
3. 每个改动取三件套：打完补丁的成品、设备上的原件、`diff -u` 出来的 `.diff`。三件齐了才算可重放，只留成品以后无法回退也无法判断改了什么。
4. 归档 README 必须写三段：哈希表（成品与原件各自的 sha256 和字节数）、重放命令（先备份原件再覆盖、可执行位单独 chmod）、以及"哪个升级命令会重新铺平这个目录"的提醒。
5. 取回后用 `shasum`/`sha256sum` 与设备侧记录逐个对，一致才提交。

## 踩过的坑
- 把"打包时打过补丁的脚本"当成品去取回，会取回一份干净的原文：一次性补丁是在 `/tmp` 里解包副本上打完立即执行、不落盘的，重启即消失。这种补丁没有可复制成品，只能留重放脚本并在 README 里点明"不会再回落到包内文件"。
- `scp` 封装脚本的参数顺序（本机→设备 or 设备→本机）极易搞反，反了不报错、只是静默留下空文件；取回后必须立刻 `ls -l` + 哈希核对，不能只看退出码。
- 升级路径（如 `mu300-update apply` 重铺 `/opt`）会把这些补丁覆盖回原样，README 不写这一句，下次装完就莫名其妙失效。

## 可复用的产物或模板
```sh
# 设备侧记基准
sha256sum /path/bin/tool /path/bin/tool.bak-YYYYMMDD
# 取回（本机侧，方向：设备→本机）
scp -O root@<dev>:<远端路径> <本地路径>
# 生成差异
diff -u tool.orig tool > tool.diff
# 覆盖后复验
printf 'AT+CLCC\n' | tool -t 6 -
```
