# F50（MU300 / UMS9620）OpenWrt 数据联网修复

设备：`192.168.77.1`，内核 `5.4.254-gb50db5b6224c`，OpenWrt `25.12.5 r33051-f5dae5ece4`
SIM：联通（当前 APN 为空，走网络默认承载）

## 结论

数据联网已经打通：`sipa_eth0` 拿到运营商地址、默认路由、DNS 全就位，设备自身与 LAN 侧都可出网。
**问题不在 SIM、不在 APN、不在防火墙**，卡点是上游一条"就绪接口读不到就不许开 PDP"的闸，在 5.4 这版
vendor 驱动上是误判。

## 根因

`/opt/mu300/bin/mobile-data` 在注册完成后、`AT+CGACT` 之前，会调用
`MU300_DELE_WAIT=20 /opt/mu300/bin/sipa-dele-start`，失败就：

```
sipa delegate did not become ready; refusing unsafe PDP activation   → exit 1
```

`sipa-dele-start` 的 `delegate_ready()` 要求
`/sys/bus/platform/drivers/sipa_delegate/*/sipa_dele_wait` 恰好存在一个，读到 1 才算就绪。

实测这颗 5.4 模块**根本没有这个属性**：

- `sipa-dele.ko` 的字符串里没有任何 `sipa_dele_wait` / `sipa_dele_wait_show`（6.18 那颗才有 `channel_wait`、`sipa_dele_wait_show`）
- 实际 sysfs 目录只有 `sipa_dele_reset` 一个节点
- 脚本日志：`missing or ambiguous kernel readiness interface; matching delegate module required`

但"没就绪接口"≠"委托没工作"。模块本身是由脚本在**注册完成之后**才 insmod 的（时间点是对的），
委托线程是活的——实测放行后 `sipa_eth0` 的 `rx_packets` 立刻开始增长，下行正常。

## 修法

只改一处：`/opt/mu300/bin/sipa-dele-start` 的 `delegate_ready()`，把"读不到就绪节点"从硬失败
改成"模块已经加载则记一句日志并继续"，模块未加载时仍然拒绝（保留真正危险的早加载场景）。

```sh
    [ "$count" = 1 ] || {
        if ! grep -q '^sipa_dele ' /proc/modules; then
            log 'missing or ambiguous kernel readiness interface; matching delegate module required'
            return 1
        fi
        log 'no readiness sysfs on this 5.4 vendor driver build; module loaded after registration, proceeding'
        return 0
    }
```

原件备份：`/opt/mu300/bin/sipa-dele-start.bak-20261107`（5024 字节，10-26）。

改完 `sh -n` 语法校验通过，然后 `ifdown wan; ifup wan`：

```
"up": true  "l3_device": "sipa_eth0"  ipv4 10.64.128.144/8
ping 223.5.5.5 → 2/2 通（52–136 ms）
/tmp/mu300-sipa-dele.log: no readiness sysfs on this 5.4 vendor driver build ...
```

## 热点/局域网客户端"无互联网"（第二个坑，同样致命）

现象：设备自身 ping/HTTP 全通，手机连上 `ZTE-F50` 也拿到 DHCP（192.168.77.206），但手机上显示无互联网。

根因不在 NAT、不在 DNS、不在桥接（`br-lan` 成员是 `wlan0` + `usb0`，DHCP 租约正常），而在**整张防火墙规则表压根没加载**：

```
/etc/init.d/firewall restart
  flowtable ft {
            ^^
  /dev/stdin:95:3-44: Error: Could not process rule: No such file or directory
          meta l4proto { tcp, udp } flow offload @ft;
  The rendered ruleset contains errors, not doing firewall restart.
```

`flowtable ft` 的 `devices = { "br-lan", "sipa_eth0" }` 里，`sipa_eth0` 是自定义 ARPHRD（`link/[519]`）的虚拟口，
内核不接受它进 flowtable，于是 fw4 整表拒绝应用，跑的还是旧表——旧表里 `chain accept_to_wan` 是空的，
而 `chain forward` 的 policy 是 `drop`，局域网客户端的包全被丢掉。设备自身的流量不经过 forward 链，
所以"设备能上网、客户端不能"。

修法：

```sh
uci set firewall.@defaults[0].flow_offloading='0'
uci commit firewall
/etc/init.d/firewall restart
```

（另外给 wan zone 显式补了一条 `option device 'sipa_eth0'`，避免它依赖 interface 展开。）

修复后实际生效：

```
chain accept_to_wan {
    oifname "sipa_eth0" ct state invalid counter drop  "!fw4: Prevent NAT leakage"
    oifname "sipa_eth0" counter packets 3 bytes 192 accept  "!fw4: accept wan IPv4/IPv6 traffic"
}
```

conntrack 里客户端已经正常 NAT 出网：

```
udp src=192.168.77.206 dst=40.99.93.210:443  →  reply src=40.99.93.210 dst=10.142.189.242
```

代价是关掉了软件流卸载（这台机器是转发型用途，影响不大；换来的是规则表能正常加载）。

## 原版 mu300 是怎么做的（实测可用，但最终未采用）

> **最终采用的是“关闭软件流卸载”**（见上一节）：`flow_offloading=0` 让 fw4 压根不生成 flowtable，
> 5.4 那个 EBUSY 冲突从源头消失，手工 reload / LuCI 保存防火墙都安全。上游那套钩子方案已实测通过
> （含一次冷启动），但依赖一个额外的 hotplug 文件，且覆盖不到非 ifup 的 reload，故撤下留档：
> 钩子脚本本地备份 `修复脚本/19-mu300-fw4-钩子版.sh`，要回退就把该文件放回
> `/etc/hotplug.d/iface/19-mu300-fw4`（755）、`uci set firewall.@defaults[0].flow_offloading='1'` 再 restart。

上游从来不关 offload，它有两件配套的东西：

1. **`openwrt/patches/fw4-sipa-offload.patch`** —— 改 `/usr/share/ucode/fw4.uc`，把 `sipa_eth0` 补进设备发现：

```ucode
/* mu300cell exposes sipa_eth0 as l3_device only, so fw4's
 * physical-device discovery misses its software ingress hook. */
if (fs.access('/sys/class/net/sipa_eth0'))
    push(devices, 'sipa_eth0');
```

本机这版 `fw4.uc` 已经被厂商改过（`unisoc-flowtable-ports-v1`，第 541 行起），
里面已有等价逻辑：“Include active L3-only protocols in their configured zones”
（遍历 zone 的 network，`net?.up && net.device` 就纳入）。所以**这条不用再打补丁**。

2. **`openwrt/overlay/etc/hotplug.d/iface/19-mu300-fw4`** —— 5.4 内核的 flowtable 事务坑：

fw4 是“先 `flush table inet fw4`、再重建整张表”的原子事务。5.4 的 `nf_tables_newflowtable`
会拒绝一个“命名了同一张表里另一个 flowtable 用过的设备”的 flowtable，而同事务里刚删掉的那张
还算在里面（跳过 inactive 条目的检查是 5.13 之后才有的）。于是
`flowtable ft { ... } Error: Resource busy` → 整笔事务失败 → 设备上留下的还是 S19 那版规则
（那时 netifd 还没建 br-lan 和 sipa_eth0，没有 LAN input 规则、没有 masquerade）。
上游的解法：在 ifup 触发的 reload 之前，**单独一笔事务**先把 `flowtable inet fw4 ft` 删掉，
reload 再重建它，事务就过了。只在 5.4、只在 ifup 时动作。

已装到设备：`/etc/hotplug.d/iface/19-mu300-fw4`（755），并把 `flow_offloading` 恢复为 1、
撤掉之前手工加的 `zone wan device='sipa_eth0'`（fw4.uc 自己会从 network 解析）。

### 本机与上游的差异（必须改一处）

上游脚本删的是 `flowtable inet fw4 ft`。**这颗厂商 5.4 内核直接拒绝**：

```
nft delete flowtable inet fw4 ft   → Error: Could not process rule: Resource busy
nft flush flowtable inet fw4 ft    → Error: Could not process rule: Resource busy
```

只要 flowtable 已注册，任何对它的删/flush 都是 EBUSY（连表项都清不掉）。但**删整张表可以**：

```
nft delete table inet fw4   → rc=0
```

所以本机钩子写成先试 flowtable、失败再删整表：

```sh
nft delete flowtable inet fw4 ft 2>/dev/null || nft delete table inet fw4 2>/dev/null
logger -t mu300 "..."
```

紧跟着的 `20-firewall` 会把整表重建（含 flowtable 与 masquerade），中间那一下没有规则的空窗
只在 ifup 瞬间，可以接受。

验证（模拟 ifup + 手工 reload）：

```
flowtable ft { devices = { "br-lan", "sipa_eth0" } }
chain accept_to_wan {
    oifname "sipa_eth0" ct state invalid counter drop
    oifname "sipa_eth0" counter packets 2 bytes 150 accept
}
客户端 conntrack: 192.168.77.206 → 17.57.145.27:5223 ESTABLISHED [ASSURED]
```

上游自己也记了未覆盖的情况：**非 ifup 触发的 reload**（LuCI 里保存防火墙、手工 `fw4 reload`）
在 5.4 上仍会失败，需要先 `nft delete flowtable inet fw4 ft; fw4 reload`。

## 最终状态（关闭卸载方案）

```sh
uci set firewall.@defaults[0].flow_offloading='0'
uci commit firewall
/etc/init.d/firewall restart
```

- `flowtable` 对象不再生成，`accept_to_wan` 正常带上 `sipa_eth0`；
- `19-mu300-fw4` 钩子已从设备删除（本地留档，见上）；
- **手工 `firewall reload` / LuCI 保存防火墙都可以随便做了**（实测 `rc=0`，规则与 NAT 都正确）。

验证（当前状态实测）：

```
uci get firewall.@defaults[0].flow_offloading → 0
nft list flowtables inet fw4 → 无 flowtable
accept_to_wan: oifname "sipa_eth0" ... accept（已计数 63 包 / 11437 字节）
forward: policy drop
srcnat_wan: masquerade
/etc/init.d/firewall reload → rc=0，重载后 sipa_eth0 规则仍在
```

## 内核切到 6.18（当前运行 6.18.60）

用上游自带的 `mu300-update`（就是之前撤掉的那个“内核切换页面”背后的同一个工具，命令行直接调）：

```sh
/opt/mu300/bin/mu300-update kernel 6.18
```

切换前的保险：

- boot_b（`/dev/mmcblk0p38`，64MB）整分区备份到
  `/mnt/mu300-disk/boot/boot_b-backup-before-6.18.img`，sha256 前 16 位 `829272d50a5bdf2a`
- 工具自身：`slot b armed: 5 failed boot(s) in a row before Android`（连挂 5 次自动退回 Android 引导）
  失败可 `mu300-update rollback-boot`

切换输出：

```
boot: 2956 modules for 6.18.60 installed into: openwrt
boot: updated to v2026.11.02.1 (kernel 24930312 bytes, ramdisk 15367184 bytes)
kernel 6.18 selected.
```

重启后实测（`uname -r` = `6.18.60`，uptime 62s）：

| 项目 | 结果 |
|---|---|
| 数据拨号 | `up=true`、`sipa_eth0` 10.162.134.165/8，另有 IPv6 `2408:8430:831:2be1:...` |
| sipa 委托 | 日志 `delegate channel and resource callbacks ready`；6.18 上 `sipa_dele_wait`／`sipa_dele_ready` 都在 |
| 设备出网 | ping 223.5.5.5 65ms |
| 防火墙 | `accept_to_wan` 正常带 `sipa_eth0`（已在计数） |
| 客户端 | ping 33ms、HTTPS 200（192.168.77.142 走 F50） |
| **通话（airsim/ALSA）** | **失效** |

通话失效的原因写得很直白：

```
the audio extra has drivers for 5.4.254-gb50db5b6224c and this is 6.18.60:
a newer mu300-audio may have this kernel's
```

`luci-app-airsim` 带的音频附加包里的驱动只编了 5.4 那版，6.18 下 `/etc/init.d/airsim` 起不来
（`active with no instances`）。要恢复语音只有两条路：等/找带 6.18 驱动的新版 audio 附加包，
或者 `mu300-update rollback-boot` 退回 5.4。

结论：**6.18 上数据联网比 5.4 还干净**（sipa 有真正的就绪接口，不用我们那个放行补丁；
mainline 内核也没有 5.4 的 flowtable 事务坑），代价是语音没了。

## 已知遗留

- 冷启动链路已在“关卸载”配置下验证过两次重启（wan 自动 up、`sipa_eth0` 拨号成功、客户端出网）。
- 若之后有人把 `flow_offloading` 改回 1（比如 LuCI 里勾上“软件流量分载”），5.4 的坑立刻回来：
  表现为客户端断网而设备自身正常，`accept_to_wan` 为空。要么改回 0，要么按上面钩子方案回退。
- 三家运营商换卡：移动 `cmnet`、电信 `ctnet`（部分卡 `ctnet@mycdma.cn`），联通当前走默认承载；
  设备无内置 APN 库，换卡后在 LuCI APN 页手填。
- 下行时延观感偏大（个别 ping 300 ms+），`AT+CSQ: 99,99` 说明信号强度读不出来，
  若实际信号弱会影响速率；与本次改动无关。
